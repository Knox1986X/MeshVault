# Спецификация формата контейнера MeshVault Format v1 и машин состояний

## 1. Модель границ безопасности (Zero Plaintext on Disk)

Главный инвариант MeshVault: на флеш-памяти Android, SSD CachyOS, во временных каталогах (`/tmp`, `cacheDir`) и в Dropbox (`/MeshVault/`) никогда не сохраняются незашифрованные медиафайлы, превью, имена файлов, дерево папок, теги, заметки или EXIF.

```text
+-----------------------------------------------------------------------------+
|                        НЕДОВЕРЕННОЕ ХРАНИЛИЩЕ (ДИСК / DROPBOX)              |
|  vault.header + vault.header.bak | catalog/tree.mvc | blobs/<2h>/<uuid>.mvb |
|  thumbs/pack_<uuid>.mvt          | wal/import.wal   | audit/security.mvc    |
|  (только AEAD-шифротекст, случайные UUID, нонсы, соли и Poly1305-теги)      |
+--------------------------------------+--------------------------------------+
                                       | Чтение / запись по 1 МиБ или 4 МиБ
                                       v
+-----------------------------------------------------------------------------+
|                    ДОВЕРЕННАЯ ГРАНИЦА (ОЗУ / RUST CORE)                     |
|  1. Argon2id / Keystore / Recovery Kit -> KEK -> расшифровка MVK в SecretBox|
|  2. MVK -> расшифровка catalog/tree.mvc и per-file FEK в ОЗУ                |
|  3. FEK -> потоковая AEAD-расшифровка отдельных чанков по 1 МиБ в буфер ОЗУ |
|  4. ZeroizeOnDrop + mlock (Linux) при блокировке или завершении сессии      |
+--------------------------------------+--------------------------------------+
                                       | Поток пикселей / PCM / ByteBuffer
                                       v
+-----------------------------------------------------------------------------+
|                    РЕНДЕР В ОЗУ (ANDROID / CACHYOS UI)                      |
|  Android: Compose ImageBitmap + Media3 Custom DataSource + FLAG_SECURE      |
|  CachyOS: Tauri v2 in-memory protocol + скрытие при потере фокуса           |
|  При переходе в Locked: немедленное зануление MVK и сброс кэша декодера     |
+-----------------------------------------------------------------------------+
```

## 2. Иерархия ключей (Envelope Encryption)

1. `FEK` (File Encryption Key, 256 бит): отдельный случайный ключ из `OsRng` для каждого медиафайла `.mvb` и каждого пака миниатюр `.mvt`.
2. `MVK` (Master Vault Key, 256 бит): главный ключ сейфа. Шифрует каталог, обёртывает каждый `FEK` (XChaCha20-Poly1305, AAD = `MVLT-FEK-WRAP-V1 || file_uuid`) и порождает доменно-разделённые подключи через `blake3::derive_key`:
   - `MeshVault v1 Catalog Master Key` — ключ каталога папок и медиа;
   - `MeshVault v1 Keyed Dedup BLAKE3` — приватный ключ дедупликации внутри сейфа;
   - `MeshVault v1 Search Index Key` — ключ локального поискового и OCR-индекса;
   - `MeshVault v1 Thumbnail Index Key` — ключ индекса паков превью;
   - `MeshVault v1 Security Audit Log Key` — ключ локального журнала событий безопасности.
3. `KEK` (Key Wrapping Key, 256 бит): ключ слота заголовка. Обёртывает `MVK` независимо в каждом активном слоте. Смена пароля или перепривязка биометрии обновляет только `vault.header` и `vault.header.bak` без перешифровки медиафайлов.

## 3. Структура каталогов контейнера

```text
<vault_root>/
  vault.header          # Основной бинарный заголовок с ревизией R
  vault.header.bak      # Теневая копия заголовка для атомарного отката
  catalog/
    tree.mvc            # Зашифрованное дерево папок, медиа, тегов, заметок и корзины
  blobs/
    <2_hex_uuid>/
      <uuid_hex>.mvb    # Зашифрованный медиафайл в чанках по 1 МиБ
  thumbs/
    pack_<uuid>.mvt     # Зашифрованный пак миниатюр (целевой размер 4 МиБ)
  wal/
    import.wal          # Зашифрованный/транзакционный журнал докачки импорта
```

## 4. Бинарный формат заголовка (`vault.header` и `vault.header.bak`)

Все целые числа кодируются в `little-endian`, UUID — 16 байт big-endian (`uuid::Uuid::as_bytes`).

| Смещение | Размер (байт) | Поле | Описание |
| :--- | :--- | :--- | :--- |
| 0 | 4 | `magic` | Константа `MVLT` (`0x4D 0x56 0x4C 0x54`) |
| 4 | 2 | `format_version` | Версия формата (`1` для MeshVault Format v1) |
| 6 | 2 | `flags` | Битовые флаги (`1 << 0` — паддинг размеров, `1 << 1` — decoy-режим) |
| 8 | 16 | `vault_id` | Уникальный UUID сейфа |
| 24 | 8 | `revision` | Монотонно растущий номер ревизии заголовка (`u64 LE`) |
| 32 | 8 | `created_at_unix_ms` | Время создания сейфа в миллисекундах Unix (`u64 LE`) |
| 40 | 4 | `argon2_memory_kib` | Память Argon2id в КиБ (по умолчанию `65536` = 64 МиБ) |
| 44 | 4 | `argon2_iterations` | Число итераций Argon2id (по умолчанию `3`) |
| 48 | 4 | `argon2_parallelism` | Число потоков Argon2id (по умолчанию `1`) |
| 52 | 2 | `slot_count` | Количество слотов ключей (`u16 LE`) |
| 54 | `121 * slot_count` | `slots[]` | Массив слотов ключей |
| конец | 32 | `header_blake3` | BLAKE3-хеш всех предыдущих байтов заголовка |

### Формат записи `KeySlot` (121 байт)

| Смещение в слоте | Размер | Поле | Описание |
| :--- | :--- | :--- | :--- |
| 0 | 16 | `slot_id` | UUID слота |
| 16 | 1 | `slot_type` | `1` = PassphraseArgon2id, `2` = HardwareKeystore, `3` = RecoveryKit24, `4` = Fido2Hmac, `5` = DecoyPassphrase |
| 17 | 32 | `salt` | Криптографическая соль (`OsRng`) |
| 49 | 24 | `wrap_nonce` | Случайный 192-битный нонс XChaCha20-Poly1305 |
| 73 | 48 | `wrapped_mvk` | 32 байта `MVK` + 16 байт тега Poly1305 |

AAD каждого слота (47 байт): `MVLT-SLOT-V1 (12B) || vault_id (16B) || format_version (2B LE) || slot_id (16B) || slot_type (1B)`.

### Атомарное обновление и восстановление заголовка

Запись выполняется через временный файл -> `fsync` -> `rename` сначала для `vault.header`, затем для `vault.header.bak`. При загрузке читаются обе копии, у каждой проверяется `header_blake3`, и выбирается валидный заголовок с максимальным `revision`.

## 5. Формат потоковых зашифрованных чанков (`blobs/<2h>/<uuid>.mvb`)

### 5.1. Прелюдия блоба (`BlobPrelude`, 48 байт)

| Смещение | Размер | Поле | Описание |
| :--- | :--- | :--- | :--- |
| 0 | 4 | `magic` | Константа `MVB1` |
| 4 | 16 | `file_id` | UUID медиафайла |
| 20 | 4 | `chunk_size` | Размер открытого чанка в байтах (по умолчанию `1048576` = 1 МиБ) |
| 24 | 24 | `base_nonce` | Случайный базовый 192-битный нонс (`OsRng`) |

### 5.2. Чанки с произвольным доступом O(1)

Каждый чанк `i` (`0, 1, ..., total_chunks - 1`) шифруется алгоритмом `XChaCha20-Poly1305`:
- Детерминированный 24-байтный нонс чанка:
  `XOF(blake3::derive_key("MeshVault v1 Chunk Nonce", base_nonce || file_id || i_le_u64 || is_final_u8))[0..24]`
- Associated Authenticated Data (33 байта):
  `MVB1 (4B) || file_id (16B) || i_le_u64 (8B) || is_final_u8 (1B) || plaintext_len_le_u32 (4B)`
- Нефинальный чанк всегда содержит ровно `chunk_size` байт открытого текста и занимает ровно `stride = chunk_size + 16` байт шифротекста.
- Пустой файл (0 байт) записывается как 1 финальный чанк с 0 байт открытого текста (16 байт тега Poly1305), чтобы исключить незамеченную обрезку до 48-байтной прелюдии.
- Позиция чанка `i` на диске вычисляется за O(1):
  `offset(i) = 48 + i * (chunk_size + 16)`
- Общее число чанков определяется по длине файла `blob_len`:
  `total_chunks = ceil((blob_len - 48) / (chunk_size + 16))`
- Защита от атак:
  - Подмена любого байта шифротекста, тега или прелюдии -> отказ тега Poly1305.
  - Перестановка двух чанков `i` и `j` -> несовпадение `chunk_index` в нонсе и AAD -> отказ аутентификации.
  - Обрезка конца последнего чанка или удаление целого последнего чанка -> предыдущий чанк имеет `is_final = 0`, поэтому при проверке последнего наблюдаемого чанка с `is_final = 1` аутентификация гарантированно падает.

## 6. Формат паков превью (`thumbs/pack_<uuid>.mvt`) и каталога (`catalog/tree.mvc`)

### 6.1. Паки превью (`.mvt`)

- Целевой размер пака: `4 МиБ` (`4 * 1024 * 1024` байт), чтобы не плодить десятки тысяч мелких файлов в SAF/Android и скрывать точное количество и размер отдельных миниатюр в Dropbox.
- Каждый пак имеет собственный `FEK`, обёрнутый `MVK`, и состоит из заголовка `MVT1` и последовательности аутентифицированных записей миниатюр.
- Координаты каждой миниатюры `(pack_id, offset, len)` хранятся внутри зашифрованного каталога (`ThumbLocator`).

### 6.2. Зашифрованный каталог (`catalog/tree.mvc`)

| Смещение | Размер | Поле | Описание |
| :--- | :--- | :--- | :--- |
| 0 | 4 | `magic` | Константа `MVC1` |
| 4 | 16 | `vault_id` | UUID сейфа |
| 20 | 8 | `catalog_revision` | Номер ревизии каталога (`u64 LE`) |
| 28 | 24 | `nonce` | Случайный 192-битный нонс (`OsRng`) |
| 52 | N | `ciphertext_and_tag` | XChaCha20-Poly1305 шифротекст JSON/CBOR-модели дерева папок и медиа |

AAD каталога: `MVLT-CATALOG-V1 || vault_id (16B) || catalog_revision (8B LE)`.

## 7. Три главные машины состояний и восстановление после сбоев

### 7.1. Конвейер импорта (`crates/meshvault-import`)

Инвариант: исходные файлы пользователя **никогда** не удаляются до состояния `CatalogCommitted`.

| Текущее состояние | Событие | Следующее состояние | Запись в журнал `wal/import.wal` |
| :--- | :--- | :--- | :--- |
| `ScanningTree` | Обход дерева завершён и подсчитан вес | `PreviewReady` | Список узлов дерева, `job_id`, отметки исключённых веток |
| `PreviewReady` | Пользователь подтвердил импорт | `ImportingChunks` | План элементов `item_id`, `target_folder_id`, статус `Pending` |
| `ImportingChunks` | Пауза от пользователя / нехватка заряда | `Paused` | Индекс последнего подтверждённого чанка `verified_chunks` |
| `ImportingChunks` | Ошибка чтения / битый файл / 0 байт | `Quarantined` | Причина ошибки для итогового отчёта карантина |
| `ImportingChunks` | Все чанки файла записаны во временный блоб | `VerifyingTags` | `verified_chunks = total_chunks`, ожидаемый размер |
| `VerifyingTags` | Все Poly1305-теги файла проверены | `CatalogCommitted` | Запись нового `catalog/tree.mvc`, отметка `Committed` в WAL |
| `VerifyingTags` | Сбой верификации или I/O | `Quarantined` | Удаление недописанного блоба `.mvb.part`, запись в отчёт |
| `CatalogCommitted` | Пользователь выбрал удаление оригиналов | `OptionalSourceCleanup` | Флаг запроса `MediaStore.createDeleteRequest` |
| `CatalogCommitted` | Удаление оригиналов не требуется | `Completed` | Очистка завершённой транзакции из `import.wal` |
| `OptionalSourceCleanup` | Системное подтверждение удаления завершено | `Completed` | Очистка завершённой транзакции из `import.wal` |
| Любое активное | Отмена пользователем до коммита | `Aborted` | Удаление недописанных `.mvb.part`, фиксация в WAL |

Восстановление после убийства процесса: при старте сканируется `wal/import.wal`. Элементы в статусе `ImportingChunks` или `VerifyingTags` проверяются по последнему целому чанку или перешифровываются заново с оригинала; недокоммиченные `.mvb.part` без записи `CatalogCommitted` безопасно удаляются, оригиналы пользователя остаются нетронутыми.

### 7.2. Состояние безопасности сейфа (`crates/meshvault-ffi`)

| Текущее состояние | Событие | Следующее состояние | Действие с ключами и UI |
| :--- | :--- | :--- | :--- |
| `Locked` | Запрос биометрии | `UnlockingBiometric` | Вызов Android Keystore / Secret Service без раскрытия MVK |
| `Locked` | Ввод мастер-пароля | `UnlockingPassphrase` | Вычисление Argon2id KEK в ОЗУ |
| `UnlockingBiometric` | Биометрия изменена или отменена | `UnlockingPassphrase` | Отказ аппаратного ключа -> переход на мастер-пароль |
| `UnlockingPassphrase` | Успешное снятие обёртки стандартного слота | `UnlockedFull` | Загрузка `MVK` в `SecretBox`, расшифровка `catalog/tree.mvc` |
| `UnlockingPassphrase` | Введён PIN/пароль принуждения | `UnlockedDecoy` | Открытие независимого decoy-контейнера без раскрытия основного MVK |
| `UnlockedFull` | Включён режим демонстрации с рук | `UnlockedSafePresentation` | Фиксация разрешённого списка ID, блокировка папок и свойств |
| `UnlockedSafePresentation` | Подтверждение биометрией или PIN | `UnlockedFull` | Снятие ограничений показа |
| `UnlockedFull` / `UnlockedSafePresentation` / `UnlockedDecoy` | Автолок / Flip-to-Lock / `Ctrl+L` / USB-триггер | `LockingZeroize` | Сигнал немедленного сброса декодеров и UI-кэша |
| `LockingZeroize` | Очистка памяти завершена | `Locked` | `Zeroize` для `MVK`, подключей, FEK и очистка буфера обмена |

Восстановление после убийства процесса: все ключи существуют исключительно в ОЗУ, поэтому после внезапного убийства процесса ОС система всегда стартует строго в состоянии `Locked` с нулевыми остаточными секретами на диске.

### 7.3. Синхронизация (`crates/meshvault-sync`)

| Текущее состояние | Событие | Следующее состояние | Запись в журнал синхронизации |
| :--- | :--- | :--- | :--- |
| `IdleOffline` | Включён sync и доступна разрешённая сеть | `CheckingRemoteEpoch` | Локальная эпоха `local_epoch` и хеш каталога |
| `CheckingRemoteEpoch` | Сеть сменилась на лимитную / низкий заряд | `PausedMetered` | Сохранение состояния паузы и списка pending-блобов |
| `CheckingRemoteEpoch` | Есть новые локальные блобы | `UploadingBlobs` | Список загружаемых UUID блобов и чанков |
| `UploadingBlobs` | Все блобы загружены, удалённая эпоха новее | `DownloadingMissingManifest` | Сохранение подтверждённых удалённых блобов |
| `CheckingRemoteEpoch` | Удалённая эпоха новее локальной | `DownloadingMissingManifest` | Целевая `remote_epoch` и индекс блобов |
| `DownloadingMissingManifest` | Манифест и журнал операций получены | `MergingCatalog` | Сохранение скачанного удалённого каталога во временный буфер ОЗУ |
| `MergingCatalog` | Обнаружены конкурентные правки папок/тегов | `ConflictResolved` | Журнал детерминированного слияния CRDT/op-log |
| `MergingCatalog` / `ConflictResolved` | Слияние завершено без потерь | `AtomicEpochCommit` | Атомарная публикация нового зашифрованного манифеста эпохи |
| `AtomicEpochCommit` | Манифест подтверждён локально и удалённо | `Synced` | Обновление `local_epoch = remote_epoch` |

Восстановление после убийства процесса: загрузка блобов идемпотентна по UUID, а переключение удалённой эпохи происходит атомарно только в `AtomicEpochCommit` после загрузки всех новых `.mvb` и `.mvt`, поэтому оборванный sync никогда не оставляет битый манифест.
